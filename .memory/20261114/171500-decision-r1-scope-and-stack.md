# R1.0 范围与技术栈定版

- 时间：2026-11-14 17:15 (+08:00)
- 类型：decision
- 影响范围：整体
- 关联提交：初始实现

## 背景

架构设计 v3 给的是生产形态（Java 模块化单体 + 独立 Python 推理 + MySQL + 对象存储 + 队列）。
本次要交付的是"可行性验证"：本机单卡、十几份文件、能复核、能沉淀数据。

## 结论

R1.0 采用 **Python FastAPI + SQLite + 本地目录 + 无构建静态页**，不复用 Java 那一套：

| 维度 | R1.0 选择 | 生产形态（v3） | 迁移成本 |
|---|---|---|---|
| 业务编排 | Python 单进程 | Java 模块化单体 | 校验/状态机已在 `validate.py` 独立，可平移 |
| 存储 | SQLite（字段/校正表结构与 MySQL 对齐） | MySQL + 对象存储 | 换 DDL 方言 + 存储适配层 |
| 队列 | 进程内 `queue.Queue` + 1 worker | MQ / Redis | 换 `runner.enqueue` 实现 |
| 前端 | 原生 JS 静态页 | React 工作台 | 重写 UI，接口不变 |
| 推理 | 进程内 PaddleOCR | 独立推理服务 | 已有 `engines.py` 适配层可抽出 |

否决项：

- **不先写 Java**：R1.0 要验证的是"识别 + 复核 + 沉淀"链路，Java 只会把联调时间拉长。
- **不引微服务**：单卡单机，拆服务只增加部署与排障面。
- **不引 PyMuPDF**：AGPL，后续商用链路要换；改用 `pypdfium2`（Apache/BSD）。
- **不用 VL 模型跑全量**：39 s/页 + 7.9 GB 显存，只适合按页路由补手写，R1.0 不启用。

## 证据

- `python -m uvicorn backend.app.main:app` 启动后 `/api/health` 返回 ok；
- 18 份单据端到端跑通，文本层 PDF 0.14 s/份，扫描件 1.8~5.0 s/份。

## 后续

R1.1 起，若出现多租户/并发复核压力，再按 v3 拆 Java 业务层 + 推理服务。
