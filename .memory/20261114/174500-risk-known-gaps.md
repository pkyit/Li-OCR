# 风险清单：R1.0 已知漏洞与限制

- 时间：2026-11-14 17:45 (+08:00)
- 类型：risk
- 影响范围：全链路
- 状态：R1.0 明确接受，R1.1/R1.2 处理

## 1. 双引擎同源，相关错误无法互相发现（高）

PaddleOCR 与 RapidOCR 同属 PP-OCR 系（默认权重 PP-OCRv5 / PP-OCRv6），字形混淆高度相关。
实测：拍摄模糊的报销单 `BX-` 被两引擎同时识别成 `8X-`，置信度 0.93，自动通过。

- 缓解：税号校验位、金额勾稽、日期合法性等独立校验；关键字段仍需抽检。
- 彻底解决：换非同源权重或多模态复核（`NEEDS CHECK`：候选权重是否真独立）。

## 2. 自动通过 ≠ 正确（中）

"无任何可疑信号"只代表没有触发规则，不保证正确。
R1.0 的自动通过率 38.9% 不能当成准确率对外承诺。

- 缓解：文档级自动通过率与字段级错误率分开统计；关键字段建议 2% 盲抽复核。

## 3. 接口默认无鉴权（中）

`LIOCR_API_TOKEN` 为空时所有 `/api/*` 开放；服务默认只绑 `127.0.0.1`，
一旦改成 `0.0.0.0` 或部署到 K8s，**必须**设置口令（K8s 用 Secret 注入）。

- 缺口：没有用户体系、没有操作审计归属（复核人字段是自由输入）。
- 后续：接入公司 SSO + RBAC，复核人取自登录态。

## 4. 上传只校验扩展名（中）

`storage.ALLOWED_EXT` 白名单 + 200MB 上限，但没有做文件头（magic bytes）校验，
也没有解压炸弹、畸形 PDF 的防护；PDF 解析在 `pypdfium2` 进程内进行，异常会记为单据失败。

- 后续：magic bytes 校验、单页像素上限、解析超时与子进程隔离、病毒扫描。

## 5. 敏感数据落盘（中）

原始单据、页面图、OCR 文本、训练集全部在本地 `data/` 目录明文存储；
`data/` 已在 `.gitignore` 内，但磁盘本身未加密。

- 后续：磁盘加密 / 受控目录权限；生产按架构 v3 走对象存储 + WORM + 保留策略。

## 6. 前端口令存 localStorage（低）

口令保存在浏览器 localStorage，存在 XSS 时被读取的风险。
R1.0 页面无第三方脚本、无富文本渲染，风险有限；生产应改为服务端会话。

## 7. 训练标签一致性（低）

人工改过的字段不进入识别训练集（见 173500 决策），因此"最需要学习"的样本暂时只能做业务评测，
不能直接用于微调；需要词级重标注能力才能闭环。

## 8. 表格明细未解析（高，功能缺口）

银行结单的流水行没有抽取，系统对这类单据只覆盖表头字段，
"自动通过"仅代表表头无异常，**不代表明细无误**。R1.1 补齐列归属与行级复核。
